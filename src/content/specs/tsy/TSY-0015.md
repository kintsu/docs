# TSY-0015: Form Metadata Rules

## Overview

This specification defines the normative type system rules for form metadata attributes in Kintsu schemas. Form attributes (`#[form(...)]`) specify canonical messaging formats for fields without changing underlying type semantics. The system supports format variants, precision specification, encoding transforms, and format chaining with category-based validation.

Key aspects:

- **Attribute syntax**: `#[form(...)]` for outer (field-level), `#![form(...)]` for inner (namespace-level)
- **Format variants**: Built-in format identifiers for complex numbers, datetime, and serialization
- **Precision control**: Explicit precision required for all complex number forms
- **Format chaining**: Right-to-left composition with category validation
- **Custom formats**: Identifiers for media types and custom compression/encoding

## Motivation

Schema authors need to specify canonical wire formats for fields without modifying logical types. Current limitations:

1. **Complex numbers**: No standard representation across systems (polar vs cartesian, varying precision)
2. **Encoding transforms**: No schema-level way to specify base64-encoded JSON cursors
3. **Format composition**: No mechanism for chained transformations (serialize, compress, encode)

Form metadata solves these problems by providing explicit, validated format specifications at the schema level.

## Design Principles

1. **Explicit over implicit**: All complex fields require explicit form attributes
2. **Type safety**: Forms are validated against field types at compile time
3. **Category tracking**: Each format stage produces text or binary, validated for compatibility
4. **Inheritance with override**: Namespace defaults reduce boilerplate; field-level attributes override
5. **Extensibility**: Custom formats via identifiers enable future format support

## Type system rules (normative)

### Rule 1: Form attribute syntax

Form metadata uses attribute syntax with two forms:

**Outer attributes** (`#[form(...)]`):

```kintsu
#[form(polar, precision = f64)]
angle: complex
```

**Inner attributes** (`#![form(...)]`):

```kintsu
namespace physics {
    #![form(polar, precision = f64)]

    struct Wavefunction {
        amplitude: complex,
        phase: complex,
    };
}
```

**Syntax structure:**

- Outer: `#` + `[` + `form` + `(` + format-spec + `)` + `]`
- Inner: `#` + `!` + `[` + `form` + `(` + format-spec + `)` + `]`

### Rule 2: Complex number form requirement

All fields of type `complex` MUST have an explicit form attribute specifying both format variant and precision.

**Valid forms:**

```kintsu
#[form(cartesian, precision = f64)] position: complex
#[form(polar, precision = f32)] angle: complex
#[form(tuple, precision = i32)] gaussian: complex
```

**Invalid (bare complex):**

```kintsu del={1}
value: complex  // Error KFM4002: ComplexRequiresForm
```

> [!IMPORTANT]
> Bare `complex` without a form attribute is a compilation error. Use namespace-level defaults to reduce repetition.

### Rule 3: f8 minifloat form requirement

All fields of type `f8` MUST have an explicit form attribute specifying the format variant.

**Format variants:**

| Variant | Syntax          | Exponent | Mantissa | Max Value | Min Positive |
| ------- | --------------- | -------- | -------- | --------- | ------------ |
| `e4m3`  | `#[form(e4m3)]` | 4 bits   | 3 bits   | ±448      | 2^-9         |
| `e5m2`  | `#[form(e5m2)]` | 5 bits   | 2 bits   | ±57344    | 2^-16        |

**Valid forms:**

```kintsu
#[form(e4m3)] weight: f8    // Higher precision, smaller range
#[form(e5m2)] gradient: f8  // Lower precision, larger range
```

**Invalid (bare f8):**

```kintsu del={1}
value: f8  // Error KFM4003: F8RequiresForm
```

> [!IMPORTANT]
> Bare `f8` without a form attribute is a compilation error. The format variant determines range validation for f16 fallback implementations.

**f16 fallback behaviour:**

Languages without native f8 support MUST:

1. Interpret f8 values as f16
2. Reject values outside the declared format's range
3. Document the fallback behaviour

### Rule 4: Complex number format variants

| Variant     | Syntax                                | Output Structure             | Precision Types           |
| ----------- | ------------------------------------- | ---------------------------- | ------------------------- |
| `cartesian` | `#[form(cartesian, precision = <p>)]` | `{"real": <n>, "imag": <n>}` | f8, f16, f32, f64, i8-i64 |
| `polar`     | `#[form(polar, precision = <p>)]`     | `{"r": <n>, "theta": <n>}`   | f8, f16, f32, f64         |
| `tuple`     | `#[form(tuple, precision = <p>)]`     | `[<n>, <n>]`                 | f8, f16, f32, f64, i8-i64 |

**Precision constraints:**

- Float precision: `f8`, `f16`, `f32`, `f64`
- Integer precision (Gaussian integers): `i8`, `i16`, `i32`, `i64`
- Polar form does not support integer precision (angles have no meaningful integer representation)

```kintsu del={2}
#[form(cartesian, precision = i32)] gaussian: complex  // Valid: Gaussian integer
#[form(polar, precision = i32)] invalid: complex       // Error KFM2011
```

### Rule 5: String encoding forms

String fields may specify encoding forms to control character encoding validation and wire representation:

| Encoding  | Syntax             | Description                            |
| --------- | ------------------ | -------------------------------------- |
| `utf8`    | `#[form(utf8)]`    | UTF-8 (default, no attribute required) |
| `utf16`   | `#[form(utf16)]`   | UTF-16 native endian                   |
| `utf16le` | `#[form(utf16le)]` | UTF-16 little endian                   |
| `utf16be` | `#[form(utf16be)]` | UTF-16 big endian                      |
| `ascii`   | `#[form(ascii)]`   | ASCII (7-bit, strict)                  |
| `latin1`  | `#[form(latin1)]`  | ISO-8859-1 / Latin-1                   |

**Usage:**

```kintsu
#[form(utf8)] text: str       // Explicit UTF-8
#[form(utf16le)] legacy: str  // Windows-style UTF-16
#[form(ascii)] identifier: str // ASCII-only validation
```

**Validation:**

- UTF-8: Valid UTF-8 byte sequences
- UTF-16/UTF-16LE/UTF-16BE: Valid UTF-16 code units, surrogate pairs
- ASCII: Bytes 0x00-0x7F only; reject bytes >= 0x80
- Latin-1: Bytes 0x00-0xFF, direct byte-to-codepoint mapping

### Rule 5a: DateTime format variants

DateTime fields may specify format variants to control output structure:

| Variant    | Syntax              | Output Example         | Applies To         |
| ---------- | ------------------- | ---------------------- | ------------------ |
| `iso8601`  | `#[form(iso8601)]`  | `2025-12-28T21:25:45Z` | `datetime`         |
| `date`     | `#[form(date)]`     | `2025-12-28`           | `datetime`         |
| `time`     | `#[form(time)]`     | `21:25:45Z`            | `datetime`         |
| `week`     | `#[form(week)]`     | `2025-W52`             | `datetime`         |
| `week_day` | `#[form(week_day)]` | `2025-W52-7`           | `datetime`, `week` |
| `ordinal`  | `#[form(ordinal)]`  | `2025-362`             | `datetime`         |

**Builtin defaults:**

- `date` builtin: ISO 8601 date format, no form attribute required
- `week` builtin: ISO 8601 week format, no form attribute required

### Rule 6: Serialization formats

Serialization formats convert objects to text or binary representation.

**First-party formats:**

| Format    | Syntax             | Output Category | Application    |
| --------- | ------------------ | --------------- | -------------- |
| `json`    | `#[form(json)]`    | Text            | Human-readable |
| `json5`   | `#[form(json5)]`   | Text            | Relaxed JSON   |
| `yaml`    | `#[form(yaml)]`    | Text            | Configuration  |
| `toml`    | `#[form(toml)]`    | Text            | Configuration  |
| `xml`     | `#[form(xml)]`     | Text            | Legacy systems |
| `msgpack` | `#[form(msgpack)]` | Binary          | Compact binary |
| `cbor`    | `#[form(cbor)]`    | Binary          | CBOR binary    |

**Tabular formats:**

| Format    | Syntax             | Output Category | Application        |
| --------- | ------------------ | --------------- | ------------------ |
| `csv`     | `#[form(csv)]`     | Text            | Spreadsheets       |
| `tsv`     | `#[form(tsv)]`     | Text            | Tab-delimited      |
| `parquet` | `#[form(parquet)]` | Binary          | Analytics          |
| `arrow`   | `#[form(arrow)]`   | Binary          | In-memory columnar |
| `avro`    | `#[form(avro)]`    | Binary          | Hadoop ecosystem   |

### Rule 6a: Serialization format options

First-party serialization formats support optional configuration parameters:

**CSV/TSV options:**

```kintsu
#[form(csv(headers = false))] data: Record[]
#[form(csv(delimiter = "\t"))] tsv_data: Record[]  // Equivalent to tsv
#[form(csv(headers = true, delimiter = ",", quote = "\""))] standard: Record[]
```

| Option      | Type   | Default | Description                    |
| ----------- | ------ | ------- | ------------------------------ |
| `headers`   | bool   | true    | Include header row             |
| `delimiter` | string | ","     | Field delimiter                |
| `quote`     | string | "\""    | Quote character for escaping   |
| `escape`    | string | "\\"    | Escape character within quotes |

**JSON options:**

```kintsu
#[form(json(pretty = true))] debug: Response
#[form(json(indent = 4))] formatted: Config
```

| Option   | Type | Default | Description            |
| -------- | ---- | ------- | ---------------------- |
| `pretty` | bool | false   | Enable pretty printing |
| `indent` | int  | 2       | Indentation spaces     |

**YAML options:**

```kintsu
#[form(yaml(indent = 4))] config: Settings
```

| Option   | Type | Default | Description        |
| -------- | ---- | ------- | ------------------ |
| `indent` | int  | 2       | Indentation spaces |

**XML options:**

```kintsu
#[form(xml(namespace = "http://example.com/schema"))] envelope: Message
#[form(xml(declaration = true, indent = 4))] doc: Document
```

| Option        | Type   | Default | Description                |
| ------------- | ------ | ------- | -------------------------- |
| `namespace`   | string | null    | Default XML namespace      |
| `declaration` | bool   | false   | Include XML declaration    |
| `indent`      | int    | 0       | Indentation (0 = minified) |

> [!NOTE]
> `tsv` is deprecated in favor of `csv(delimiter = "\t")`. Existing `tsv` forms remain valid but emit a deprecation warning.

### Rule 7: Compression formats

Compression formats accept text or binary input and produce binary output.

| Format    | Syntax             | Input Category | Output Category | Notes                  |
| --------- | ------------------ | -------------- | --------------- | ---------------------- |
| `gzip`    | `#[form(gzip)]`    | Text or Binary | Binary          | RFC 1952               |
| `deflate` | `#[form(deflate)]` | Text or Binary | Binary          | RFC 1951 (raw deflate) |
| `zstd`    | `#[form(zstd)]`    | Text or Binary | Binary          | Zstandard              |
| `lz4`     | `#[form(lz4)]`     | Text or Binary | Binary          | Fast compression       |
| `brotli`  | `#[form(brotli)]`  | Text or Binary | Binary          | Web compression        |
| `snappy`  | `#[form(snappy)]`  | Text or Binary | Binary          | Google Snappy          |
| `lzma`    | `#[form(lzma)]`    | Text or Binary | Binary          | LZMA algorithm         |
| `xz`      | `#[form(xz)]`      | Text or Binary | Binary          | XZ Utils/LZMA2         |
| `bzip2`   | `#[form(bzip2)]`   | Text or Binary | Binary          | bzip2 compression      |

### Rule 7a: Archive formats

Archive formats wrap binary content with container metadata.

| Format | Syntax         | Input Category | Output Category | Notes                           |
| ------ | -------------- | -------------- | --------------- | ------------------------------- |
| `tar`  | `#[form(tar)]` | Binary         | Binary          | POSIX tar, no compression       |
| `zip`  | `#[form(zip)]` | Binary         | Binary          | ZIP with deflate (configurable) |
| `7z`   | `#[form(7z)]`  | Binary         | Binary          | 7-Zip archive format            |

Archive formats are primarily useful for collections of files. For single-value compression, prefer compression formats directly.

### Rule 8: Encoding formats

Encoding formats convert binary input to text output.

| Format    | Syntax             | Input Category | Output Category |
| --------- | ------------------ | -------------- | --------------- |
| `base64`  | `#[form(base64)]`  | Binary         | Text            |
| `base32`  | `#[form(base32)]`  | Binary         | Text            |
| `hex`     | `#[form(hex)]`     | Binary         | Text            |
| `ascii85` | `#[form(ascii85)]` | Binary         | Text            |

### Rule 9: Format chaining syntax

Format chaining uses `=` operator with right-to-left evaluation:

```kintsu
#[form(base64 = gzip = json)] cursor: Cursor
```

Evaluation order:

1. `json`: Serialize `Cursor` to JSON (text)
2. `gzip`: Compress JSON text to binary
3. `base64`: Encode binary to base64 text

**Syntax structure:**

```
format-chain ::= format-spec ('=' format-spec)*
format-spec  ::= identifier | identifier '(' params ')' | string-literal
params       ::= param (',' param)*
param        ::= identifier | identifier '=' value
```

### Rule 10: Format category validation

Each format produces a category (text or binary). The compiler validates category compatibility at each chain stage.

**Category rules:**

- Serialization: Objects produce Text or Binary (format-dependent)
- Compression: Text or Binary produces Binary
- Encoding: Binary produces Text

**Valid chains:**

```kintsu
#[form(base64 = gzip = json)]     // text -> binary -> text
#[form(base64 = msgpack)]         // binary -> text
#[form(gzip = base64 = json)]     // text -> text -> binary (gzip accepts text)
```

**Invalid chains:**

```kintsu del={1-2}
#[form(hex = json)]               // Error: hex requires binary, json outputs text
#[form(yaml = json)]              // Error: cannot chain serialization formats
```

### Rule 11: Custom format identifiers

Custom formats use identifiers validated against specific patterns. Custom formats **should** explicitly declare their output category to enable chain validation.

**Explicit category syntax:**

```kintsu
#[form(compress(lzo, binary))] data: Data
#[form(encode(base58, text) = gzip = msgpack)] payload: Payload
#[form(mime(application_x_custom, binary))] document: binary
```

The second positional parameter explicitly declares the output category:

- Algorithm: Lowercase snake_case identifier with optional non-starting integers (e.g., `lzo`, `base58`, `my_algo_2`)
- Category: Either `text` or `binary`

**Implicit category defaults:**

If no explicit category is declared, the compiler uses conservative defaults:

- `compress(...)`: Defaults to `binary` output
- `encode(...)`: Defaults to `text` output
- `mime(...)`: Inferred from MIME type pattern (e.g., `text_*` -> text, `application_*` -> binary)
- Type inference: From field type if rightmost transform (`str` -> text, `binary` -> binary)

> [!IMPORTANT]
> Explicit categories are **strongly recommended** for custom formats. Implicit defaults may produce incorrect validation if the custom transform has different behavior than the default.

**Media types**:

```kintsu
#[form(mime(application_pdf, binary))] document: binary
#[form(mime(application_vnd_api_json, text))] response: Data
#[form(mime(text_csv, text))] export: Record[]
```

Identifier pattern for MIME types: Convert IANA media types to snake*case (replace `/`, `-`, `.`, `+` with `*`).

**Custom compression:**

```kintsu
#[form(compress(lzo, binary))] data: binary
#[form(base64 = compress(lzo, binary) = json)] payload: Payload
```

**Custom encoding:**

```kintsu
#[form(encode(base58, text))] hash: binary
#[form(encode(base85, text) = gzip = msgpack)] data: Data
```

**Category validation:**

The compiler validates custom format categories in chain composition:

```kintsu
// Valid: lzo outputs binary, base64 accepts binary
#[form(base64 = compress(lzo, binary) = json)] cursor: Cursor

// Invalid: my_text_encoder outputs text, base64 requires binary
#[form(base64 = encode(my_text_encoder, text))] data: Data  // Error KFM2004
```

Validation pattern for custom format identifiers (lowercase snake_case with optional non-starting integers):

```regex
^[a-z][a-z0-9_]*$
```

### Rule 12: Form attribute inheritance

Inner attributes (`#![form(...)]`) provide namespace-level defaults.

**Inheritance rules:**

1. Fields without explicit form inherit from namespace-level `#![form(...)]`
2. Fields with explicit `#[form(...)]` override namespace defaults
3. Inner attributes apply to direct children only, not nested namespaces
4. Multiple inner form attributes can coexist (different purposes)

```kintsu
namespace physics {
    #![form(polar, precision = f64)]

    struct Particle {
        position: complex,   // Inherits polar, f64
        velocity: complex,   // Inherits polar, f64
        #[form(cartesian, precision = f32)] screen_pos: complex,  // Override
    };
}
```

### Rule 13: Form attribute applicability

Form attributes apply to specific schema elements:

| Element Type | Applicable | Notes                               |
| ------------ | ---------- | ----------------------------------- |
| Field        | Yes        | Primary use case                    |
| Parameter    | Yes        | Operation parameters                |
| Return type  | Yes        | Via named field wrapper             |
| Type alias   | No         | Form is field-level, not type-level |
| Struct       | No         | No clear semantics                  |
| Enum         | No         | No clear semantics                  |

```kintsu del={6-7}
// Valid: field-level
#[form(base64 = json)] cursor: Cursor

// Valid: parameter-level
operation paginate(#[form(base64 = json)] cursor: Cursor) -> Response;

// Invalid: type-level
#[form(base64 = json)]
struct Cursor { ... }  // Error KFM2006
```

## Implications

### For Schema Authors

- Complex fields require explicit form attributes with precision
- Namespace defaults reduce boilerplate for consistent formatting
- Format chains are validated at compile time
- Custom formats enable extensibility without language changes

### For Compiler Implementations

- Must parse form attribute syntax in both outer and inner positions
- Must validate format-type compatibility
- Must track format category through chain evaluation
- Must implement custom format string validation

### For Code Generators

- Form attributes inform wire encoding decisions
- Precision metadata guides numeric type selection
- Chain information enables multi-stage encoding pipelines
- Custom formats may require runtime handling or skip codegen

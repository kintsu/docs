# SPEC-0001: Builtin Type Resolution

## Overview

This SPEC defines the deterministic lookup and resolution algorithm the compiler uses to recognise builtin types, the validation expectations during decoding, and the canonical transit parsing requirements for certain builtins (notably `datetime`, `complex`, and `binary`). This document is normative for compiler behaviour. It defines the messaging protocol and compiler resolution behaviour; it does not mandate internal code-generator or runtime representations beyond the canonical transit forms.

## Resolution algorithm (deterministic)

When resolving a type token during parsing/compilation, Kintsu's compiler MUST follow the order below to guarantee deterministic results:

1. If the token is fully-qualified (contains a namespace), resolve against the explicit namespace and its imports.
2. If the token is unqualified (bare name), consult the builtin table first. If the builtin table contains the token, the token resolves to the builtin type and resolution terminates.
3. If not found in builtins, consult the local namespace symbols (types declared in the current file/module).
4. If not found locally, consult imported namespaces in the order they were declared. The first successful match wins.
5. If resolution fails at all levels, emit a `UndefinedType` diagnostic with candidate suggestions (closest lexical matches and imported namespaces where the name appears).

Notes:

- Builtin recognition takes precedence over aliases and imported types to prevent accidental shadowing of primitives.
- The builtin table is authoritative and shipped with the compiler; it can be extended only by changes to the language spec.

## Validation and parsing rules for special builtins

- `datetime`:
  - On ingress (parsing/decoding), the compiler/runtime MUST accept ISO-8601 textual forms with timezone designator. Implementations SHOULD accept common ISO-8601 variants but MUST normalise to a canonical ISO-8601 form when serialising.
  - On transit the `datetime` value is a string. Parsers that receive non-string values for `datetime` MUST emit a `TypeMismatch` diagnostic.

- `date`:
  - On ingress, the compiler/runtime MUST accept ISO-8601 date format (YYYY-MM-DD).
  - Values containing time components MUST be rejected with a `TypeMismatch` diagnostic.
  - Canonical transit form: `2025-12-28`.
  - `date` resolves as a builtin in step 2 and cannot be shadowed.

- `week`:
  - On ingress, the compiler/runtime MUST accept ISO-8601 week format (YYYY-Www or YYYY-Www-d).
  - Week number MUST be validated against ISO 8601 rules (week 01 contains the first Thursday).
  - Invalid week numbers (e.g., W54, W00) MUST emit a `ValidationError` diagnostic.
  - Canonical transit forms: `2025-W52` (week only), `2025-W52-7` (with weekday).
  - `week` resolves as a builtin in step 2 and cannot be shadowed.

- `complex`:
  - Resolution yields a composite type; the decoder MUST expect an object with numeric fields `real` and `imag`.
  - Missing components or non-numeric fields are `DecodeError` diagnostics.

- `f8`:
  - All `f8` fields MUST have an explicit `#[form(...)]` attribute specifying the format variant.
  - Two format variants are supported:
    - **E4M3**: 4 exponent bits, 3 mantissa bits, range ±448, min positive 2^-9
    - **E5M2**: 5 exponent bits, 2 mantissa bits, range ±57344, min positive 2^-16
  - Bare `f8` without form attribute MUST emit `KFM4003: F8RequiresForm`.
  - On ingress, the compiler/runtime MUST parse numeric values and validate against the declared format's range.
  - For textual transports, `f8` is represented as a numeric literal.
  - Implementations without native f8 support MUST interpret as f16 and MUST reject values outside the declared format's range.
  - `f8` resolves as a builtin in step 2 and cannot be shadowed.

- `binary`:
  - For binary transports the compiler treats `binary` as raw bytes.
  - For textual transports, `binary` fields SHOULD use `#[form(base64)]` to specify Base64 encoding.
  - When `#[form(base64)]` is present, the textual decoder MUST decode Base64 and validate byte sequences; invalid Base64 MUST emit `DecodeError`.
  - Without an explicit form, `binary` in textual context (e.g. JSON) defaults to Base64 encoding, but explicit `#[form(base64)]` is recommended for clarity.

- `i128`, `u128`:
  - 128-bit signed/unsigned integers resolve as builtins in step 2 and cannot be shadowed.
  - On ingress, the compiler/runtime MUST validate numeric values against 128-bit range.
  - Values outside $[-2^{127}, 2^{127}-1]$ (i128) or $[0, 2^{128}-1]$ (u128) MUST emit a `ValidationError` diagnostic.
  - Codegen targets MUST emit hard errors on unsupported targets; silent truncation is forbidden.
  - For textual transports, `i128`/`u128` are represented as numeric literals or strings for precision-safe transit.

- `i256`, `u256`:
  - 256-bit signed/unsigned integers resolve as builtins in step 2 and cannot be shadowed.
  - On ingress, the compiler/runtime MUST validate numeric values against 256-bit range.
  - Values outside $[-2^{255}, 2^{255}-1]$ (i256) or $[0, 2^{256}-1]$ (u256) MUST emit a `ValidationError` diagnostic.
  - Codegen targets MUST emit hard errors on unsupported targets; silent truncation is forbidden.
  - For textual transports, `i256`/`u256` MUST be represented as strings to avoid precision loss in JSON.

- `f128`:
  - IEEE 754-2008 binary128 (quad precision) resolves as a builtin in step 2 and cannot be shadowed.
  - On ingress, the compiler/runtime MUST parse IEEE 754 binary128 values.
  - Codegen targets MUST support native f128 OR emit a hard error; silent downcast to f64 is forbidden.
  - For textual transports, `f128` is represented as a numeric literal or string for precision-safe transit.

- `f256`:
  - IEEE 754-2008 binary256 (octuple precision) resolves as a builtin in step 2 and cannot be shadowed.
  - On ingress, the compiler/runtime MUST parse IEEE 754 binary256 values.
  - Codegen targets MUST support native f256 OR emit a hard error; silent downcast is forbidden.
  - For textual transports, `f256` MUST be represented as a string to avoid precision loss.
  - Most targets require library support; targets without f256 capability MUST reject schemas using f256.

- `decimal`:
  - Fixed-point decimal resolves as a builtin in step 2 and cannot be shadowed.
  - All `decimal` fields MUST have an explicit `#[form(precision = P, scale = S)]` attribute.
  - Bare `decimal` without form attribute MUST emit `KFM2017: DecimalFormRequired`.
  - Precision P must be in range 1-34 (per IEEE 754-2008); values outside this range MUST emit `KFM2021: DecimalPrecisionOutOfRange`.
  - Scale S must be in range 0-P; scale exceeding precision MUST emit `KFM2018: DecimalScaleExceedsPrecision`.
  - Backing type is derived automatically: decimal32 (P 1-7), decimal64 (P 8-16), decimal128 (P 17-34).
  - Canonical transit form: string representation of decimal value (e.g., `"12345678.90"`).

- `duration`:
  - Time duration resolves as a builtin in step 2 and cannot be shadowed.
  - All `duration` fields MUST have an explicit form attribute specifying resolution or format.
  - Bare `duration` without form attribute MUST emit `KFM2019: DurationFormRequired`.
  - Valid form variants:
    - Numeric: `#[form(ms)]`, `#[form(us)]`, `#[form(ns)]` — transit as i64 integer representing milliseconds, microseconds, or nanoseconds.
    - ISO 8601: `#[form(iso8601)]` — basic format (OnYnMnDTnHnMnS), `#[form(iso8601ext)]` — extended format.
  - Invalid form variants MUST emit `KFM2020: InvalidDurationForm`.

- `char`:
  - Unicode scalar value resolves as a builtin in step 2 and cannot be shadowed.
  - On ingress, the compiler/runtime MUST validate Unicode scalar values (U+0000 to U+10FFFF, excluding surrogates).
  - Surrogate values (U+D800 to U+DFFF) MUST emit a `ValidationError` diagnostic.
  - `char[N]` is a fixed-size string of exactly N characters.
  - Default encoding is UTF-8; charset is determined by form variant when specified (e.g., `#[form(ascii)]`, `#[form(utf16)]`).
  - Canonical transit form: single-character string.

## Integer wire encoding guidance

The type system permits multiple wire encodings. The SPEC recommends the following:

- For deterministic, simple encodings prefer fixed-size binary encodings (explicit 8/16/32/64-bit widths) and document endianness in the wire/profile.
- For compact encodings, varints or other length-encoded representations are allowed but are considered a wire/profile decision and must be documented and tested. This SPEC requires that wire/profile documentation describe encoding choices; implementations (code generators, runtimes) must not change the canonical transit protocol defined here without corresponding changes to the profile and accompanying migration guidance.

## Examples

1. Resolving `datetime` in an unqualified context binds to builtin `datetime` (step 2 above), not to an imported symbol named `datetime`.

2. An alias named `str` in a local namespace does not shadow the builtin `str` — the builtin is selected.

## Backwards compatibility and migration

Changing the builtin table is a breaking change. Any change MUST be accompanied by an AD and migration guidance. Compiler implementations should log a clear warning if a future extension adds new builtins that collide with previously used identifiers.

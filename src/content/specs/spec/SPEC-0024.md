# SPEC-0024: Form Attribute Compilation

## Overview

This specification defines the deterministic compilation and validation algorithms for form metadata attributes. The compiler parses form attributes, validates format-type compatibility, tracks format categories through chain evaluation, and stores form metadata in the AST for downstream processing.

For type system rules, see [TSY-0015](/specs/tsy/tsy-0015). For design rationale, see [RFC-0032](/specs/rfc/rfc-0032).

## Motivation

Form attribute compilation requires:

1. **Deterministic parsing**: Consistent attribute extraction across compilation runs
2. **Type-aware validation**: Format compatibility with field types
3. **Category tracking**: Valid format chains based on text/binary output categories
4. **Error generation**: Actionable diagnostics for invalid form specifications

## Architecture

### Compilation Phases

Form attribute processing occurs during the metadata resolution phase:

1. **Attribute extraction**: Parse `#[form(...)]` and `#![form(...)]` from AST
2. **Inheritance resolution**: Apply namespace defaults to fields without explicit forms
3. **Format validation**: Validate format-type compatibility
4. **Chain validation**: Track categories and validate chain compatibility
5. **AST annotation**: Store resolved form metadata for codegen

### Format Category Model

Each format produces a category that determines valid subsequent operations:

| Category | Description                 | Produced By                     |
| -------- | --------------------------- | ------------------------------- |
| Object   | Unserialised schema type    | Field type before serialisation |
| Text     | UTF-8 string representation | json, yaml, csv, base64, hex    |
| Binary   | Raw byte sequence           | msgpack, gzip, parquet          |

## Deterministic compilation rules (normative)

### Rule 1: Form attribute extraction

The compiler extracts form attributes during AST construction.

**Extraction order:**

1. Parse inner attributes (`#![form(...)]`) at namespace scope
2. Parse outer attributes (`#[form(...)]`) preceding fields/parameters
3. Store raw attribute data in AST nodes

**AST representation:**

```rust
struct FormAttribute {
    format_chain: Vec<FormatSpec>,
    precision: Option<PrecisionType>,
    span: Span,
}

enum FormatSpec {
    Builtin(BuiltinFormat),
    BuiltinWithOptions(BuiltinFormat, FormatOptions),
    Custom(CustomFormat),
}

enum BuiltinFormat {
    // String encodings
    Utf8, Utf16, Utf16Le, Utf16Be, Ascii, Latin1,
    // Complex variants
    Cartesian, Polar, Tuple,
    // DateTime variants
    Iso8601, Date, Time, Week, WeekDay, Ordinal,
    // Serialisation
    Json, Json5, Yaml, Toml, Xml, Msgpack, Cbor,
    Csv, Parquet, Arrow, Avro,
    // Compression
    Gzip, Deflate, Zstd, Lz4, Brotli, Snappy, Lzma, Xz, Bzip2,
    // Archive
    Tar, Zip, SevenZip,
    // Encoding
    Base64, Base32, Hex, Ascii85,
}

/// Format-specific configuration options
struct FormatOptions {
    options: HashMap<String, FormatOptionValue>,
}

enum FormatOptionValue {
    Bool(bool),
    Int(i64),
    String(String),
}

struct CustomFormat {
    kind: CustomFormatKind,
    algorithm: Identifier,
    /// Explicitly declared output category (second positional parameter)
    explicit_category: Option<Category>,
}

enum CustomFormatKind {
    MediaType,
    Compression,
    Encoding,
}
```

### Rule 2: Namespace inheritance resolution

The compiler resolves form inheritance before validation.

**Resolution algorithm:**

```
for each namespace N:
    extract inner form attributes as namespace_defaults[N]

for each field F in namespace N:
    if F has outer form attribute:
        resolved_form[F] = outer attribute
    else if namespace_defaults[N] exists:
        resolved_form[F] = namespace_defaults[N]
    else:
        resolved_form[F] = None
```

**Inheritance scope:**

- Inner attributes apply to direct children only
- Nested namespaces do not inherit from parent namespaces
- Field-level attributes always override namespace defaults

### Rule 3: Complex type form validation

Complex fields require explicit form with precision.

**Validation algorithm:**

```
for each field F where type(F) == complex:
    if resolved_form[F] is None:
        emit KFM4002: ComplexRequiresForm
    else if resolved_form[F].precision is None:
        emit KFM4001: MissingPrecisionParameter
    else if format is Polar and precision is integer:
        emit KFM2011: PolarFormRequiresFloatPrecision
```

### Rule 4: Format-type compatibility validation

The compiler validates that formats are applicable to field types.

**Compatibility matrix:**

| Field Type | Valid Formats                                |
| ---------- | -------------------------------------------- |
| `complex`  | cartesian, polar, tuple (with precision)     |
| `datetime` | iso8601, date, time, week, week_day, ordinal |
| `date`     | (implicit iso8601), week_day                 |
| `week`     | (implicit iso8601), week_day                 |
| User types | Serialisation formats, encoding chains       |
| `binary`   | Encoding formats, compression, media types   |

**Validation algorithm:**

```
for each field F with resolved_form:
    format = resolved_form[F].format_chain[0]  // rightmost in chain
    if not compatible(type(F), format):
        emit KFM2001: FormIncompatibleWithFieldType
```

### Rule 4a: bf16 form validation

The compiler validates that `bf16` form is only applied to `f32` fields.

**Validation algorithm:**

```
for each field F with resolved_form:
    if resolved_form[F].format_chain contains "bf16":
        if type(F) != f32:
            emit KFM2015: Bf16RequiresF32
        else:
            annotate AST node with bf16 flag for codegen
```

**Codegen contract:** bf16-annotated f32 fields use brain float format (1 sign, 8 exponent, 7 mantissa) with range ±3.39×10³⁸ and reduced precision. See [OCP MX Specification v1.0](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf) for format details.

### Rule 4b: e8m0 form validation

The compiler validates that `e8m0` form is only applied to `u8` fields.

**Validation algorithm:**

```
for each field F with resolved_form:
    if resolved_form[F].format_chain contains "e8m0":
        if type(F) != u8:
            emit KFM2016: E8m0RequiresU8
        else:
            annotate AST node with e8m0 flag for codegen
```

**Codegen contract:** e8m0-annotated u8 fields represent shared scaling exponents for MX block formats. Range is 2⁻¹²⁷ to 2¹²⁷. See [OCP MX Specification v1.0](https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf) for usage patterns.

### Rule 4c: decimal form validation

The compiler validates that `decimal` fields have explicit form with precision and scale.

**Validation algorithm:**

```
for each field F where type(F) == decimal:
    if resolved_form[F] is None:
        emit KFM2017: DecimalFormRequired
    else:
        parse form as (precision = P, scale = S)
        if P not in range 1-34:
            emit KFM2021: DecimalPrecisionOutOfRange
        if S > P:
            emit KFM2018: DecimalScaleExceedsPrecision
        else:
            annotate AST node with precision and scale for codegen
```

**Codegen contract:** Precision determines backing storage per IEEE 754-2008:

| Precision Range | Backing Type | Coefficient Digits |
| --------------- | ------------ | ------------------ |
| 1-7             | decimal32    | 7                  |
| 8-16            | decimal64    | 16                 |
| 17-34           | decimal128   | 34                 |

### Rule 4d: duration form validation

The compiler validates that `duration` fields have explicit form specifying resolution or format.

**Validation algorithm:**

```
for each field F where type(F) == duration:
    if resolved_form[F] is None:
        emit KFM2019: DurationFormRequired
    else:
        form = resolved_form[F].format_chain[0]
        if form not in {ms, us, ns, iso8601, iso8601ext}:
            emit KFM2020: InvalidDurationForm
        else:
            annotate AST node with duration form for codegen
```

**Codegen contract:**

| Form       | Wire Type | Semantics                                                          |
| ---------- | --------- | ------------------------------------------------------------------ |
| ms         | i64       | Milliseconds since epoch                                           |
| us         | i64       | Microseconds since epoch                                           |
| ns         | i128      | Nanoseconds since epoch                                            |
| iso8601    | string    | ISO 8601 duration format (e.g., `P1DT2H3M4S`)                      |
| iso8601ext | string    | Extended ISO 8601 with fractional seconds (e.g., `P1DT2H3M4.567S`) |

### Rule 5: Format chain category validation

The compiler tracks category at each chain stage.

**Category transition rules:**

| Format Type   | Input Category | Output Category |
| ------------- | -------------- | --------------- |
| Serialisation | Object         | Text or Binary  |
| Compression   | Text or Binary | Binary          |
| Encoding      | Binary         | Text            |
| Charset       | Text           | Text            |

**Charset encoding:**

Charset transforms (`utf8`, `utf16`, `utf16le`, `utf16be`, `ascii`, `latin1`) may only appear as the outermost (leftmost) transform in a chain and require text input. They specify the byte encoding of the final text output.

```
for each field F with format_chain:
    if format_chain[0] is charset_encoding:
        if format_chain[1..].final_category != Text:
            emit KFM2004: ChainingCompatibilityViolation
        annotate AST node with charset for codegen
```

**Validation algorithm:**

```
for each field F with format_chain:
    category = Object
    for format in format_chain (right to left):
        (valid, new_category) = validate_transition(category, format)
        if not valid:
            emit KFM2004: ChainingCompatibilityViolation
        category = new_category
```

**Category determination for serialisation formats:**

| Format  | Output Category | Notes |
| ------- | --------------- | ----- |
| json    | Text            |       |
| json5   | Text            |       |
| yaml    | Text            |       |
| toml    | Text            |       |
| xml     | Text            |       |
| csv     | Text            |       |
| msgpack | Binary          |       |
| cbor    | Binary          |       |
| parquet | Binary          |       |
| arrow   | Binary          |       |
| avro    | Binary          |       |

### Rule 6: Custom format validation

Custom formats are validated as identifiers and must have explicit or inferable output categories.

**Syntax parsing:**

```
custom-format  ::= function-call
function-call  ::= identifier '(' argument [',' category] ')'
argument       ::= identifier | string-literal
category       ::= 'text' | 'binary'
identifier     ::= [a-z][a-z0-9_]*
string-literal ::= '"' <any-char-except-quote>* '"'
```

**Identifier validation:**

- Lowercase snake_case with optional non-starting integers
- Regex pattern: `^[a-z][a-z0-9_]*$`
- Examples: `lzo`, `base58`, `my_algo_2`

**MIME type validation:**

- `mime()` function accepts a literal string as the first argument
- String MUST be a valid IANA media type per [RFC 6838](https://datatracker.ietf.org/doc/html/rfc6838)
- Examples: `mime("application/pdf", binary)`, `mime("text/csv", text)`

**Category determination algorithm:**

```
for each custom_format in format_chain:
    // 1. Check for explicit category (second parameter)
    if custom_format.explicit_category is Some:
        output_category = custom_format.explicit_category

    // 2. Apply implicit defaults based on function name
    else:
        match custom_format.kind:
            Compression:
                output_category = Binary
            Encoding:
                output_category = Text
            MediaType:
                // Infer from MIME pattern in algorithm identifier
                if algorithm starts_with "text_":
                    output_category = Text
                else:
                    output_category = Binary

    // 3. Validate chain compatibility
    if next_format exists:
        validate_transition(output_category, next_format)
```

### Rule 7: AST annotation

After validation, the compiler annotates AST nodes with resolved form metadata. The internal AST representation tracks:

- Format chain in sequence order (outermost to innermost)
- Precision for complex/f8 types
- Final output category (text/binary)
- Whether the form was inherited from namespace defaults

For the JSON serialization format used in declaration bundles, see [RFC-0021: Declaration Bundle Format](/specs/rfc/rfc-0021#form-metadata).

### Rule 8: Diagnostic span attachment

Error diagnostics attach spans to the relevant source locations.

**Span rules:**

| Error Type          | Primary Span             | Related Spans   |
| ------------------- | ------------------------ | --------------- |
| ComplexRequiresForm | Field declaration        | Type annotation |
| MissingPrecision    | Form attribute           | Format variant  |
| IncompatibleFormat  | Format in chain          | Field type      |
| ChainCompatibility  | Incompatible format pair | Previous format |
| InvalidCustomFormat | Identifier               | -               |

## Design Principles

1. **Fail fast**: Detect errors during compilation, not codegen
2. **Precise diagnostics**: Attach errors to exact source locations
3. **Deterministic**: Same input produces same output across runs
4. **Extensible**: Custom formats enable future format support

## Implications

### For Compiler Implementers

- Form attributes are processed during metadata resolution phase
- Category tracking requires state management through chain evaluation
- Custom format validation requires regex matching
- AST storage must preserve inheritance information for codegen

### For Code Generators

- Access resolved form metadata via AST annotations
- `final_category` indicates wire representation (text/binary)
- `inherited` flag distinguishes explicit from default forms
- Custom formats may require skip or deferred handling

### For Tooling

- IDE completion can suggest valid formats based on field type
- Linters can warn about redundant explicit forms matching defaults
- Documentation generators can extract format specifications

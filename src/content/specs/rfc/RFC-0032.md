# RFC-0032: Form Metadata Design

## Abstract

This RFC establishes the design rationale for form metadata attributes (`#[form(...)]`), new temporal builtins (`date`, `week`), and the `f8` numeric builtin. Form attributes enable schema authors to specify canonical messaging formats for fields without changing underlying type semantics. The design addresses use cases including cursor pagination, complex number representation, ISO date formatting, and ML/AI workloads requiring low-precision floats.

## Motivation

### Canonical Format Specification

Schema authors need to specify how values are serialized for transit without modifying the logical type. Current limitations:

1. **Complex numbers**: No standard representation. Different systems use polar vs cartesian, tuple vs object, varying precision.
2. **Temporal data**: `datetime` is overloaded. Many APIs need date-only or week-only values but lack type-level guarantees.
3. **Cursor pagination**: Opaque cursors typically require base64-encoded JSON, but this pattern has no schema-level representation.
4. **ML/AI workloads**: 8-bit floats are increasingly common but unsupported by current builtins.

### Design Goals

1. **Explicit format contracts**: Schema defines canonical wire format, not implementation details
2. **Type safety**: Format must be compatible with field type; compiler validates
3. **Composability**: Formats can be chained (serialization, compression, encoding)
4. **No implicit defaults**: Complex numbers require explicit precision to prevent security issues

## Specification

### New Builtins

**Temporal builtins**:

| Builtin | Syntax | Canonical Transit Form | ISO 8601 Reference |
| ------- | ------ | ---------------------- | ------------------ |
| `date`  | `date` | `2025-12-28`           | Date without time  |
| `week`  | `week` | `2025-W52`             | Week date          |

**Numeric builtin**:

| Builtin | Syntax | Description                       | Requires Form | Fallback         |
| ------- | ------ | --------------------------------- | ------------- | ---------------- |
| `f8`    | `f8`   | 8-bit minifloat (IEEE 754 subset) | Yes           | Interpret as f16 |

**f8 format variants**:

| Variant | Syntax          | Exponent | Mantissa | Max Value | Min Positive | Use Case             |
| ------- | --------------- | -------- | -------- | --------- | ------------ | -------------------- |
| `e4m3`  | `#[form(e4m3)]` | 4 bits   | 3 bits   | ±448      | 2^-9         | Higher precision     |
| `e5m2`  | `#[form(e5m2)]` | 5 bits   | 2 bits   | ±57344    | 2^-16        | Larger dynamic range |

### Form Attribute Syntax

Form attributes specify canonical messaging formats using outer (`#[form(...)]`) and inner (`#![form(...)]`) attribute syntax.

**Simple format variants**:

```kintsu title="schema/types.ks"
#[form(polar, precision = f64)] angle: complex
#[form(cartesian, precision = f32)] position: complex
#[form(week_day)] start: week
#[form(e4m3)] weight: f8   // Higher precision f8
#[form(e5m2)] gradient: f8 // Larger range f8
```

**Encoding transforms** (right-to-left composition):

```kintsu title="schema/api.ks"
#[form(base64 = gzip = json)] cursor: Cursor
```

Evaluation: `Cursor` object serialized to JSON (text), compressed with gzip (binary), encoded as base64 (text).

```sh title="Serialize"
echo '{"page":1,"next_page":2,"size":25}' | gzip | base64

---
H4sIAJwCUmkAA6tWKkhMT1WyMtRRykutKImH8Ix0lIozq0AM01ouAANOcQsjAAAA
---
```

```sh title="Deserialize"
echo "H4sIAJwCUmkAA6tWKkhMT1WyMtRRykutKImH8Ix0lIozq0AM01ouAANOcQsjAAAA" | base64 -D | gzip -d | jq .next_page
---
2
---
```

> [!NOTE]
> Cursors would be smaller as base64 in practice; We use it for demonstrative purposes only

**Namespace defaults**:

```kintsu title="schema/api.ks"
namespace physics {
    #![form(polar, precision = f64)]

    struct Wavefunction {
        amplitude: complex,  // Inherits polar, f64
        phase: complex,      // Inherits polar, f64
    };
}
```

### Complex Number Precision Requirement

All complex fields MUST have an explicit `#[form(...)]` attribute specifying both format and precision. Bare `complex` without form triggers compilation error.

**Supported precision types**:

| Form        | Supported Precision                  | Use Case                           |
| ----------- | ------------------------------------ | ---------------------------------- |
| `cartesian` | f8, f16, f32, f64, i8, i16, i32, i64 | General purpose, Gaussian integers |
| `polar`     | f8, f16, f32, f64                    | Angles, phasors (float only)       |
| `tuple`     | f8, f16, f32, f64, i8, i16, i32, i64 | Compact representation             |

**Gaussian integers**: Integer precision (i8-i64) supports Gaussian integers for number theory and lattice cryptography applications. Polar form does not support integer precision as angles have no meaningful integer representation.

```kintsu title="schema/math.ks"
#[form(cartesian, precision = i32)] gaussian: complex  // Valid: Gaussian integer
#[form(polar, precision = i32)] invalid: complex       // Error: polar requires float
```

### f8 Minifloat Form Requirement

All f8 fields MUST have an explicit `#[form(...)]` attribute specifying the format variant (e4m3 or e5m2). Bare `f8` without form triggers compilation error.

**Trade-offs between variants**:

| Variant | Precision | Range  | Best For                        |
| ------- | --------- | ------ | ------------------------------- |
| `e4m3`  | Higher    | ±448   | Model weights, fine-grained ops |
| `e5m2`  | Lower     | ±57344 | Gradients, activations          |

**f16 fallback with range clamping**:

Languages without native f8 support MUST:

1. Interpret f8 values as f16
2. Validate that incoming values fall within the declared format's range
3. Reject out-of-range values with `KFM2012: F8ValueOutOfRange`

This ensures semantic correctness even when the target lacks native f8 support.

```kintsu title="schema/ml.ks"
#[form(e4m3)] weight: f8      // Valid: range ±448
#[form(e5m2)] gradient: f8    // Valid: range ±57344
value: f8                     // Error: KFM4003 F8RequiresForm
```

### Format Category Model

Format transformations follow a three-stage pipeline:

1. **Serialization** (Objects to Text or Binary): json, yaml, msgpack, etc.
2. **Compression** (Text/Binary to Binary): gzip, zstd, lz4, brotli
3. **Encoding** (Binary to Text): base64, hex, ascii85

Each stage produces a category (text or binary) that determines valid subsequent stages.

### Text Charset Encoding

When a format chain produces text output, an optional charset encoding may be applied as the outermost transform:

```kintsu
#[form(utf16 = base64 = gzip = json)] payload: Payload
#[form(utf16le = encode(base58, text) = gzip = msgpack)] cursor: Cursor
```

This is necessary because "text" as an output category is semantically a character sequence, but the underlying byte representation depends on the charset. Default is UTF-8, but explicit charset allows interoperability with systems expecting specific encodings.

### Custom Formats

Custom formats use identifiers with optional category declarations:

**Media types** (using `mime()` function with IANA media type strings per [RFC 6838](https://datatracker.ietf.org/doc/html/rfc6838)):

```kintsu
#[form(mime("application/pdf", binary))] document: binary
#[form(mime("application/vnd.api+json", text))] response: Data
```

MIME types MUST be valid IANA registered media types. The first parameter is a literal string containing the IANA media type; the second parameter specifies the output category.

**Custom compression/encoding**:

```kintsu
#[form(compress(snappy) = json)] data: Data
#[form(encode(base58, text) = gzip = msgpack)] payload: Payload
```

## Rationale

### Why Explicit Precision for Complex?

Implicit precision defaults create security and compatibility risks:

1. **32-bit system compatibility**: Default f64 may overflow or truncate on 32-bit targets
2. **Codegen safety**: If codegen ignores precision constraints, data corruption occurs
3. **Self-documenting schemas**: Explicit precision makes schema intent clear

The decision to require explicit precision for ALL complex forms (not just polar) ensures consistency and prevents surprises when schema authors switch between cartesian and polar representations.

### Why New Temporal Builtins?

The `datetime` builtin is overloaded for use cases that don't require time components:

1. **Date-only APIs**: Birth dates, expiration dates, holidays
2. **Week-based scheduling**: ISO week calendars, fiscal weeks
3. **Type-level guarantees**: `date` cannot accidentally include timezone/time

Form attributes on `datetime` (e.g., `#[form(date)]`) provide formatting but not type safety. New builtins provide compile-time guarantees.

### Why f8 with Explicit Format?

8-bit floats are increasingly important for:

1. **ML/AI inference**: Model weights, activations
2. **Bandwidth efficiency**: 8x reduction vs f64
3. **Hardware acceleration**: TPUs, specialized accelerators

Two dominant f8 formats exist in the ML ecosystem:

- **E4M3**: Higher precision (3 mantissa bits), smaller range (±448). Used for weights.
- **E5M2**: Lower precision (2 mantissa bits), larger range (±57344). Used for gradients.

Requiring explicit format specification:

1. **Forces conscious choice**: Schema author must consider precision/range trade-off
2. **Enables range validation**: f16 fallback implementations can reject out-of-range values
3. **Self-documenting**: Format choice reveals intent

Languages without native f8 support can interpret as f16 with range clamping. This ensures semantic correctness: a value declared as e4m3 will be rejected if it exceeds ±448, even on systems using f16 internally.

### Why bf16 as Form on f32?

bfloat16 is modelled as a form on f32 rather than a distinct builtin:

1. **Same semantic range**: bf16 has identical exponent range to f32
2. **Implementation flexibility**: Targets choose native bf16 or f32 fallback
3. **No form variants**: Single format means no explicit form choice needed
4. **Clear fallback path**: f32 is the natural upcast target

**bf16 Format Specification:**

| Property      | Value          |
| ------------- | -------------- |
| Sign bits     | 1              |
| Exponent bits | 8              |
| Mantissa bits | 7              |
| Bias          | 127            |
| Max value     | ~3.4 × 10^38   |
| Min positive  | ~1.18 × 10^-38 |

**Semantics:**

- bf16 preserves f32 exponent range with reduced mantissa precision
- Transit encoding uses 16 bits (truncated f32)

**Codegen contract:**

- Codegen targets MAY reject schemas using unsupported forms
- Codegen targets MAY emit f16/f32/f64 fallback with documented behaviour
- Codegen targets SHOULD emit comments indicating fallback behaviour
- Users MUST implement their own range checks for custom targets

### Why e8m0 as Form on u8?

The e8m0 scale type is modelled as a form on u8 rather than a distinct builtin:

1. **Storage representation**: e8m0 is stored as an unsigned 8-bit value
2. **Semantic annotation**: Form attribute adds scale factor semantics
3. **Implementation simplicity**: Targets store as u8, apply scale interpretation
4. **Limited applicability**: Only meaningful in MX block contexts

**e8m0 Format Specification:**

| Property      | Value           |
| ------------- | --------------- |
| Sign bits     | 0 (unsigned)    |
| Exponent bits | 8               |
| Mantissa bits | 0               |
| Bias          | 127             |
| Range         | 2^-127 to 2^127 |
| NaN           | 0xFF            |

**Semantics:**

- Values represent power-of-two scale factors: 2^(value - 127)
- Zero is not representable (minimum is 2^-127)
- 0xFF encodes NaN (invalid scale)
- Used as block scale in OCP MX microscaling formats

### Codegen Requirements for Extended Types

**Extended width integers (i128, u128, i256, u256):**

- Codegen targets MUST emit hard errors on unsupported targets (not silent truncation)
- Codegen targets MAY support targets with library extensions (e.g., Python + PyArrow, Python + web3.py)
- Codegen targets SHOULD document supported target + library combinations

Security rationale: Silent overflow from 128-bit to 64-bit or 256-bit to lower widths creates security vulnerabilities. Hard errors force explicit handling.

**Quad-precision float (f128):**

- Codegen targets MUST support native f128 OR emit hard error
- Silent downcast to f64 is forbidden (precision loss)
- Library support counts as target support

### Why i128/u128 as Core Types?

128-bit integers are added as core builtins rather than forms because:

1. **Semantic distinctness**: 128-bit integers represent fundamentally different ranges than 64-bit
2. **Security implications**: Silent truncation from 128 to 64 bits causes overflow vulnerabilities
3. **Real-world usage**: Cryptocurrency, UUIDs, and high-precision counters require 128 bits
4. **Language support**: Rust has native i128/u128; other languages have library support

Codegen produces hard errors on unsupported targets. A target is "supported" if the language OR a standard library provides 128-bit integer support (e.g., Python + PyArrow).

### Why i256/u256 as Core Types?

256-bit integers are added as core builtins because:

1. **Cryptographic use cases**: Semantic representation of cryptographic values and hash outputs
2. **Blockchain interoperability**: Many blockchain systems use 256-bit as the native word size
3. **SHA-256 outputs**: Hash functions produce 256-bit values requiring native representation
4. **Security implications**: Same as 128-bit; silent truncation is forbidden

Codegen produces hard errors on unsupported targets. Library support counts (e.g., Python + web3.py).

### Why f128 as Core Type?

Quad-precision float is added as a core builtin per IEEE 754-2008:

1. **Standard compliance**: binary128 is a normative IEEE 754 format
2. **Scientific computing**: Some simulations require extended precision
3. **Intermediate precision**: Financial calculations may need f128 for intermediate results
4. **Clear semantics**: Unlike x87 extended precision, f128 has precise semantics

Codegen produces hard errors on unsupported targets. Silent downcast to f64 is forbidden.

### Why f256 as Core Type?

Octuple-precision float is added as a core builtin per IEEE 754-2008:

1. **Standard compliance**: binary256 is a normative IEEE 754-2008 format
2. **Extreme precision**: Research applications requiring precision beyond quad
3. **Completeness**: Full coverage of IEEE 754-2008 binary interchange formats
4. **Software emulation**: Most targets will require library support, which is acceptable

Codegen produces hard errors on unsupported targets. Silent downcast to f128 or lower is forbidden. Most practical use cases are served by f128 or decimal; f256 is included for completeness and specialised research applications.

### Why NOT f96/f80?

x87 extended precision (80-bit, often padded to 96 bits) is excluded:

1. **Not IEEE 754**: binary128 is standard; 80-bit extended is x87 legacy
2. **Platform dependence**: NumPy's float96 is actually 80-bit on x86, 64-bit on Windows
3. **No portable semantics**: Behaviour varies across platforms
4. **Limited utility**: Modern code uses f64 or f128, not legacy extended

If x87 compatibility is needed, use platform-specific libraries.

### Why NOT f4/f6 as Core Types?

OCP MX defines E2M1 (f4) and E3M2/E2M3 (f6) formats. These are excluded because:

1. **Best practices vs. standards**: OCP is an industry consortium, not IEEE or ISO
2. **Format maturity**: Sub-byte floats are evolving; premature standardisation risks obsolescence
3. **Limited interoperability**: No mainstream languages support f4/f6 natively
4. **Semantic alternatives**: Integer types with documented scaling achieve similar results

May be reconsidered if OCP MX formats achieve broader adoption and stability.

### Why decimal with Required Form?

Decimal is a core type with required form because:

1. **Parameterised precision**: Unlike float types, decimals need precision/scale specification
2. **Financial requirements**: Exact decimal arithmetic avoids binary floating-point errors
3. **Standard compliance**: IEEE 754-2008 defines decimal32/decimal64/decimal128 semantics
4. **Automatic backing selection**: Backing type derived from precision per IEEE specification

The form syntax `#[form(precision = P, scale = S)]` specifies precision P (1-34) and scale S (0-P).

**IEEE 754-2008 backing selection:**

| Precision | Backing    |
| --------- | ---------- |
| 1-7       | decimal32  |
| 8-16      | decimal64  |
| 17-34     | decimal128 |

**Codegen contract:**

- Targets MAY upcast to higher precision (range-inclusive)
- Targets MUST preserve at minimum the specified precision and scale
- Targets SHOULD emit diagnostics when upcasting

### Why duration with Required Form?

Duration requires form because:

1. **Resolution ambiguity**: "duration" without resolution is meaningless
2. **Multiple representations**: Numeric (ms/us/ns) vs string (ISO 8601)
3. **Standard compliance**: ISO 8601 defines duration formats precisely
4. **Codegen clarity**: Form determines underlying type (i64 vs str)

### Why char Type?

The `char` type is added for fixed-size strings:

1. **Array semantics**: `char[N]` is naturally a fixed N-character string
2. **Avoids confusion**: `str[N]` would appear to be "array of N strings"
3. **Encoding forms**: `char` supports same encoding forms as `str`
4. **Rust precedent**: Rust distinguishes `char` (scalar value) from `str` (string slice)

### Why NOT udecimal?

Unsigned decimal is omitted for now:

1. **IEEE 754 decimals are signed**: The standard includes a sign bit
2. **Future range annotations**: Explicit range constraints (e.g., `#[range(0, max)]`) will address unsigned semantics
3. **Validation vs. type**: Unsigned is often a validation constraint, not a type distinction

### Why NOT time Type?

A separate `time` (time of day) type is excluded:

1. **Not semantically distinct**: Time of day is duration since midnight
2. **Clear alternatives**: `time: u64 // ms since midnight` is explicit
3. **Standard alignment**: Neither Protobuf nor Arrow has distinct time-of-day type
4. **Reduced complexity**: Fewer types means simpler type system

### Why Right-to-Left Composition?

The syntax `#[form(base64 = gzip = json)]` reads naturally as a pipeline:

- Rightmost: Input format (json serializes object)
- Middle: Transformation (gzip compresses)
- Leftmost: Output format (base64 encodes for text transport)

This mirrors Unix pipeline semantics (`json | gzip | base64`) and functional composition.

### Why Explicit Categories for Custom Formats?

Custom format transforms are user-defined functions (UDFs) for serialization. Without explicit output categories, the compiler cannot validate format chains:

1. **Validation safety**: `compress(lzo)` might output binary, but custom `compress(my_algo)` could output text
2. **Future-proofing**: New compression algorithms may have different output characteristics
3. **Self-documenting**: Explicit category parameter makes the transform's contract clear

Example validation failure without explicit categories:

```kintsu
// Custom format outputs text, but base64 requires binary input
#[form(base64 = transform(custom_algo))] data: Data  // Would fail during generation!
```

With explicit categories:

```kintsu
// Compiler catches incompatibility at compile time
#[form(base64 = transform(custom_algo, text))] data: Data  // Error: base64 requires binary input
```

**Implicit defaults** (`compress(...)` defaults to binary, `encode(...)` defaults to text) provide convenience but may be incorrect for custom implementations. Explicit categories treat custom formats as first-class UDFs with typed interfaces.

**Identifier format**: Algorithm names use lowercase snake_case with optional non-starting integers (e.g., `lzo`, `base58`, `my_algo_2`), avoiding quoting complexity and treating them as first-class language identifiers.

### Alternatives Considered

**Implicit f64 default for complex**: Rejected due to 32-bit compatibility and derived security concerns.

**Form attributes on type definitions**: Rejected because format is a field-level concern, not a type-level property. A `Cursor` type might be base64-encoded in one API and raw JSON in another.

**Unix timestamps for datetime**: Rejected because ISO 8601 is the established transit standard and provides human readability.

**Hardcoded category inference for custom formats**: Rejected because it assumes all `compress(...)` functions output binary, which may not hold for custom implementations.

## Acceptance Criteria

- [ ] AC-1: `date`, `week`, and `f8` builtins are recognised by the compiler
- [ ] AC-2: `#[form(...)]` and `#![form(...)]` syntax is parsed and validated
- [ ] AC-3: Bare `complex` without form attribute produces compilation error (KFM4002)
- [ ] AC-4: Bare `f8` without form attribute produces compilation error (KFM4003)
- [ ] AC-5: Polar form with integer precision produces compilation error
- [ ] AC-6: Format chaining validates category compatibility at each stage
- [ ] AC-7: Custom format strings are validated against documented patterns
- [ ] AC-8: Namespace-level form defaults are inherited by child fields
- [ ] AC-9: f16 fallback implementations reject values outside declared f8 format range

## Keyword Identifier Rules

Kintsu allows keywords to be used as field identifiers for ergonomic JSON/wire compatibility. This avoids awkward renaming when schema fields naturally match language keywords.

**Permitted contexts for keyword identifiers:**

- Field names in structs
- Parameter names in operations
- Enum variant names

**Forbidden contexts for keyword identifiers:**

- Type names (struct, enum, error, oneof)
- Type aliases
- Operation names
- Namespace names

**Syntax disambiguation:**

Parsers disambiguate keywords from field identifiers by lookahead for the `:` separator (ignoring whitespace without line breaks). Syntax highlighters should apply the same heuristic.

```kintsu title="Valid: keywords as field names"
struct Event {
    date: date,      // Field 'date' of type date
    week: week,      // Field 'week' of type week
    struct: Nested,  // Field 'struct' of user type
}
```

```kintsu title="Invalid: keywords as type names" del={1,4}
struct date { ... }      // Error: 'date' is a keyword

namespace api {
    type week = str;     // Error: 'week' is a keyword
}
```

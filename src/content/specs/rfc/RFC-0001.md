# RFC-0001: Builtin Type System Design

## Abstract

This RFC captures the design rationale and non-normative guidance for Kintsu's builtin type set. It describes the goals, trade-offs, and recommended transit representations that downstream code-generators and runtime libraries should follow. The aim is to standardize interoperability for message/schema transit while leaving room for pluggable wire encodings.

## Motivation

Kintsu is a schema and message type system intended primarily for transit (message/schema) use — similar in intent to protobuf/gRPC style systems. A small, well-understood set of builtin scalar and primitive types makes code generation, validation, and cross-language compatibility tractable. This RFC documents the rationale for the chosen builtins and provides recommended canonical transit forms so that independent implementations can interoperate.

## Specification

This RFC is non-normative. Normative semantics (syntax, validation, and resolution) are specified in [TSY-0001](/specs/tsy/tsy-0001) and [SPEC-0001](/specs/spec/spec-0001).

Builtins (authoritative list):

- bool
- str
- i8, i16, i32, i64, i128, i256
- u8, u16, u32, u64, u128, u256
- f8, f16, f32, f64, f128, f256
- decimal
- complex
- datetime
- date
- week
- duration
- char
- never
- binary

Key decisions captured here:

- **Datetime** is always represented as a string on the wire and MUST use an ISO-8601 compliant textual form including timezone information (e.g. `2025-10-30T14:23:00Z` or `2025-10-30T09:23:00-05:00`). Implementations may accept equivalent forms when parsing, but the canonical transit form is ISO-8601 with timezone designator.

- **Date** is a lower-precision temporal type representing a calendar date without time component. Canonical transit form is ISO-8601 date: `2025-12-28`. This type provides type-level guarantees against accidental timezone or time inclusion.

- **Week** is an ISO 8601 week date type. Canonical transit forms: `2025-W52` (week only) or `2025-W52-7` (with weekday when `#[form(week_day)]` applied). Week 01 is defined as the week containing the first Thursday of the year per ISO 8601.

- **f8** is an 8-bit minifloat supporting two format variants: E4M3 (4 exponent bits, 3 mantissa bits) and E5M2 (5 exponent bits, 2 mantissa bits). Intended for ML/AI workloads where low precision is acceptable. Like `complex`, all `f8` fields MUST have an explicit `#[form(...)]` attribute specifying the format variant. Languages without native f8 support MUST interpret as f16, clamping values to the format-specific range:

  | Variant | Max Value | Min Positive | Max Negative | Syntax                  |
  | ------- | --------- | ------------ | ------------ | ----------------------- |
  | E4M3    | 448       | 2^-9         | -448         | `#[form(e4m3)] val: f8` |
  | E5M2    | 57344     | 2^-16        | -57344       | `#[form(e5m2)] val: f8` |

  Parsing clients using f16 fallback MUST reject values outside the declared format's range.

- **i128/u128** are 128-bit integer types for use cases requiring extended precision beyond 64-bit: cryptocurrency balances, UUID numeric representation, high-precision distributed counters, and cryptographic intermediate values. Codegen targets MUST emit hard errors on unsupported targets (not silent truncation). Library support counts (e.g., Python + PyArrow).

- **i256/u256** are 256-bit integer types for blockchain and cryptographic use cases: semantic representation of cryptographic values, hash output representation (SHA-256), and interoperability with systems using 256-bit word sizes. Same codegen requirements as 128-bit types.

- **f128** is IEEE 754-2008 binary128 (quad precision): 128 bits, 1 sign bit, 15 exponent bits, 112 mantissa bits, bias 16383. Used for scientific computing requiring extended precision and financial calculation intermediates. Codegen targets MUST support native f128 OR emit hard error. Silent downcast to f64 is forbidden.

- **f256** is IEEE 754-2008 binary256 (octuple precision): 256 bits, 1 sign bit, 19 exponent bits, 236 mantissa bits, bias 262143. Used for extremely high-precision scientific computing and arbitrary-precision arithmetic research. Codegen targets MUST support native f256 OR emit hard error. Silent downcast to lower precision is forbidden.

- **decimal** is a fixed-point decimal type with configurable precision and scale. Requires explicit form: `#[form(precision = P, scale = S)]` where P is total significant digits (1-34) and S is digits after decimal point (0 to P). Backing type derived automatically per IEEE 754-2008: decimal32 (P 1-7), decimal64 (P 8-16), decimal128 (P 17-34). Codegen targets MAY upcast to higher precision but MUST preserve at minimum the specified precision and scale.

- **duration** is a time span type requiring explicit form specifying resolution or format. Numeric forms: `#[form(ms)]`, `#[form(us)]`, `#[form(ns)]` store as i64. String forms: `#[form(iso8601)]` for basic ISO 8601 duration (OnYnMnDTnHnMnS), `#[form(iso8601ext)]` for extended format (PYYYYMMDDThhmmss). Bare `duration` without form is a compilation error.

- **char** is a single Unicode scalar value (U+0000 to U+10FFFF, excluding surrogates). `char[N]` is a fixed-size string of exactly N characters. `char[]` (unsized array) is semantically equivalent to `str`. The default encoding is UTF-8, but the charset is determined by form variant when specified (e.g., `#[form(ascii)]`, `#[form(utf16)]`). Supports all encoding forms that `str` supports.

- Complex numeric values are represented as objects (struct-like) with named components (see [TSY-0001](/specs/tsy/tsy-0001)). This keeps the representation explicit and portable across languages that lack a native complex scalar.

- Kintsu supports multiple wire/encoding styles. For integer wire encodings the recommended/suggested approach is fixed-size (e.g., 8/16/32/64-bit little/big-endian as defined by a chosen wire profile) to keep determinism and simple alignment. Alternative encodings (e.g., varint or strict-length encodings) are allowed per wire profile. The choice is intentionally left to the wire/profile (see SPEC). Implementations and wire/profile documentation MUST explicitly document the chosen encoding for each target/profile — this specification defines the messaging protocol and normative transit forms, not internal code-generator representations.

- Binary data has a binary wire representation (raw bytes) and an interoperable textual form (`#[form(base64)]`) when appropriate. Users may use `#[form(base64)]` on `binary` fields to specify base64 encoding for textual transports.

Examples (non-normative):

1. Datetime transit (canonical):

```json
"2025-10-30T14:23:00Z"
```

2. Complex transit (canonical object form):

```json
{ "real": 1.5, "imag": -0.25 }
```

3. Binary textual transit (when the transport is textual):

```json
"SGVsbG8sIHdvcmxkIQ==" // base64("Hello, world!")
```

4. Date transit (canonical):

```json
"2025-12-28"
```

5. Week transit (canonical):

```json
"2025-W52"      // week only
"2025-W52-7"    // with weekday (Sunday)
```

6. f8 transit (textual, numeric value):

```json
1.5
```

7. decimal transit (precision 10, scale 2):

```json
"12345678.90"
```

8. duration transit (milliseconds form):

```json
3600000
```

9. duration transit (ISO 8601 form):

```json
"P1DT12H30M"
```

10. char transit (single character):

```json
"A"
```

## Rationale

The goal is secure, clear, and portable transit semantics:

- **Datetime-as-string (ISO-8601)**: many languages and libraries already support ISO-8601 parsing and formatting; carrying timezone information removes ambiguity about instant vs local time. Using strings in transit avoids cross-platform issues with epoch-endian differences and sub-second representations.

- **Date and Week builtins**: these precision-appropriate temporal types provide type-level guarantees. A `date` field cannot accidentally include time or timezone information, reducing a class of bugs where code assumes local midnight or UTC boundaries. The `week` type supports business logic that operates on ISO weeks (common in European scheduling, accounting, and logistics).

- **Complex-as-object**: not all target languages have a built-in complex scalar. Representing complex numbers as objects with `real` and `imag` ensures every language can map to a concrete representation.

- **f8 minifloat**: the rise of ML/AI workloads has driven demand for low-precision floating-point types. Two dominant formats exist: E4M3 (higher precision, smaller range) and E5M2 (lower precision, larger range). Requiring explicit format specification via `#[form(...)]` ensures schema authors consciously choose based on their precision/range trade-off. The f16 fallback with range clamping ensures implementations can always represent f8 values while maintaining semantic correctness.

- **Integer wire encoding flexibility**: fixed-size encodings are simple and deterministic; varints are compact for small values but introduce complexity and potential cross-language surprises. Making encoding a property of the wire/profile preserves interoperability while allowing efficiency trade-offs.

- **Extended width integers (i128/u128/i256/u256)**: 128-bit integers address use cases that 64-bit cannot: cryptocurrency balances, UUID numeric representation, high-precision counters in distributed systems, and cryptographic intermediate values. 256-bit integers address blockchain and cryptographic use cases: semantic representation of cryptographic values, hash output representation (SHA-256), and interoperability with systems using 256-bit word sizes. Codegen targets MUST emit hard errors on unsupported targets because silent overflow from 128-bit to 64-bit creates security vulnerabilities.

- **Quad precision float (f128)**: IEEE 754-2008 binary128 is added for scientific computing and financial calculation intermediates. Unlike x87 extended precision (80-bit), f128 has precise cross-platform semantics. Silent downcast to f64 is forbidden due to precision loss.

- **Decimal type with required form**: Decimal is a core type with required form because decimals need precision/scale specification (unlike floats). The form syntax `#[form(precision = P, scale = S)]` specifies precision P (1-34) and scale S (0-P). Backing type is derived automatically per IEEE 754-2008.

- **Duration type with required form**: Duration requires form because a bare "duration" without resolution is meaningless. Numeric forms (ms/us/ns) store as i64; string forms (iso8601/iso8601ext) use ISO 8601 standard representations.

- **Char type for fixed-size strings**: The `char` type enables `char[N]` as a fixed N-character string. This avoids the confusion of `str[N]` appearing to be "array of N strings". The type supports same encoding forms as `str`.

- **Excluded types**: f96/f80 (x87 legacy, platform-dependent), f6/f4 (OCP MX not mature enough), f2 (negligible utility), udecimal (future range annotations), time (duration since midnight).

This RFC prefers minimalism at the language surface while delegating wire-specific efficiency decisions to wire/profile documents.

## Acceptance Criteria

The specification is accepted when the following are true:

- [ ] AC-1: The canonical builtin list is documented in `docs/src/syntax/builtin.md` and matches TSY-0001.
- [ ] AC-2: Datetime canonical transit form is documented and test vectors are present (ISO-8601 examples with offsets and Z).
- [ ] AC-3: Complex canonical form is documented (object with `real` and `imag`).
- [ ] AC-4: Guidance for integer wire encodings (recommended fixed-size; alternative encodings allowed per wire/profile) is present and linked to generator guidance.
- [ ] AC-5: Date canonical form is documented (ISO-8601 date: `YYYY-MM-DD`).
- [ ] AC-6: Week canonical form is documented (ISO-8601 week: `YYYY-Www` or `YYYY-Www-d`).
- [ ] AC-7: f8 format variants documented (E4M3, E5M2) with explicit form requirement and f16 fallback range limits.
- [ ] AC-8: Extended width integer specifications documented (i128, u128, i256, u256) with codegen contracts.
- [ ] AC-9: f128 specification documented (IEEE 754-2008 binary128) with codegen contracts.
- [ ] AC-9a: f256 specification documented (IEEE 754-2008 binary256) with codegen contracts.
- [ ] AC-10: decimal specification documented with precision/scale form syntax and backing selection.
- [ ] AC-11: duration specification documented with form variants (ms, us, ns, iso8601, iso8601ext).
- [ ] AC-12: char specification documented as Unicode scalar value with array semantics.
- [ ] AC-13: Type system comparison table included (Kintsu vs Protobuf vs Arrow vs NumPy).

## Technical Specifications

### Extended Width Integers (i128, u128, i256, u256)

| Type | Size                | Signed | Range               | Standard |
| ---- | ------------------- | ------ | ------------------- | -------- |
| i128 | 128 bits (16 bytes) | Yes    | -2^127 to 2^127 - 1 | -        |
| u128 | 128 bits (16 bytes) | No     | 0 to 2^128 - 1      | -        |
| i256 | 256 bits (32 bytes) | Yes    | -2^255 to 2^255 - 1 | -        |
| u256 | 256 bits (32 bytes) | No     | 0 to 2^256 - 1      | -        |

**Codegen contract:**

- Codegen targets MUST emit hard errors on unsupported targets (not silent truncation)
- Codegen targets MAY support targets with library extensions (e.g., Python + PyArrow, Python + web3.py)
- Codegen targets SHOULD document supported target + library combinations

Security rationale: Silent overflow from 128-bit to 64-bit or 256-bit to lower widths creates security vulnerabilities. Hard errors force explicit handling.

**Target compatibility:**

| Target           | i128/u128      | i256/u256      | Notes             |
| ---------------- | -------------- | -------------- | ----------------- |
| Rust             | Native         | Via libraries  | Native i128/u128  |
| Python + PyArrow | Yes            | No             | Via pyarrow types |
| Python + web3.py | Yes            | Yes            | Via web3 types    |
| Go               | Via big.Int    | Via big.Int    | Library support   |
| TypeScript       | Via BigInt     | Via BigInt     | Limited precision |
| Java             | Via BigInteger | Via BigInteger | Library support   |

### Quad Precision Float (f128)

| Property      | Value                   |
| ------------- | ----------------------- |
| Size          | 128 bits (16 bytes)     |
| Sign bits     | 1                       |
| Exponent bits | 15                      |
| Mantissa bits | 112                     |
| Bias          | 16383                   |
| Max value     | ~1.19 × 10^4932         |
| Min positive  | ~3.36 × 10^-4932        |
| Standard      | IEEE 754-2008 binary128 |

**Codegen contract:**

- Codegen targets MUST support native f128 OR emit hard error
- Silent downcast to f64 is FORBIDDEN (precision loss)
- Library support counts as target support

### Octuple Precision Float (f256)

| Property      | Value                   |
| ------------- | ----------------------- |
| Size          | 256 bits (32 bytes)     |
| Sign bits     | 1                       |
| Exponent bits | 19                      |
| Mantissa bits | 236                     |
| Bias          | 262143                  |
| Max value     | ~1.61 × 10^78913        |
| Min positive  | ~6.48 × 10^-78914       |
| Standard      | IEEE 754-2008 binary256 |

**Codegen contract:**

- Codegen targets MUST support native f256 OR emit hard error
- Silent downcast to f128 or lower is FORBIDDEN (precision loss)
- Library support counts as target support
- Most targets will require software emulation or specialised libraries

**Target compatibility:**

| Target | f256 Support                      | Notes                        |
| ------ | --------------------------------- | ---------------------------- |
| Rust   | Via libraries                     | No native support            |
| Python | Via mpmath                        | Arbitrary precision fallback |
| C/C++  | Via libquadmath extension or MPFR | Software emulation           |
| Go     | Via big.Float                     | Arbitrary precision          |

### Decimal Type

The `decimal` type provides exact decimal arithmetic with configurable precision and scale.

| Property  | Description                                 |
| --------- | ------------------------------------------- |
| Precision | Total significant digits (1-34)             |
| Scale     | Digits after decimal point (0 to precision) |
| Signed    | Always signed                               |
| Backing   | Automatically selected per IEEE 754-2008    |

**IEEE 754-2008 backing selection:**

| Precision Range | Backing Type | Coefficient Digits | Exponent Range | Standard Reference |
| --------------- | ------------ | ------------------ | -------------- | ------------------ |
| 1-7             | decimal32    | 7                  | -95 to +96     | IEEE 754-2008 §3.2 |
| 8-16            | decimal64    | 16                 | -383 to +384   | IEEE 754-2008 §3.2 |
| 17-34           | decimal128   | 34                 | -6143 to +6144 | IEEE 754-2008 §3.2 |

**Codegen contract:**

- Codegen targets MAY upcast to higher precision (range-inclusive)
- Codegen targets MUST preserve at minimum the specified precision and scale
- Codegen targets SHOULD emit diagnostics when upcasting

**Target compatibility:**

| Target            | decimal32 | decimal64 | decimal128 | Notes                       |
| ----------------- | --------- | --------- | ---------- | --------------------------- |
| Arrow (PyArrow)   | Yes       | Yes       | Yes        | Native support              |
| PostgreSQL        | No        | No        | Yes        | NUMERIC arbitrary precision |
| SQL Server        | No        | No        | Yes        | decimal(38, s)              |
| Java BigDecimal   | Yes       | Yes       | Yes        | Arbitrary precision         |
| Python decimal    | Yes       | Yes       | Yes        | Arbitrary precision         |
| Rust rust_decimal | No        | No        | Yes        | 96-bit coefficient          |
| C# decimal        | No        | No        | Yes        | 128-bit native              |

### Duration Type

The `duration` type represents a time span with specified resolution or format.

| Form         | Storage | Description                                 |
| ------------ | ------- | ------------------------------------------- |
| `ms`         | i64     | Milliseconds (signed)                       |
| `us`         | i64     | Microseconds (signed)                       |
| `ns`         | i64     | Nanoseconds (signed)                        |
| `iso8601`    | str     | ISO 8601 format (OnYnMnDTnHnMnS)            |
| `iso8601ext` | str     | ISO 8601 extended format (PYYYYMMDDThhmmss) |

### Char Type

| Property   | Value                                     |
| ---------- | ----------------------------------------- |
| Definition | Single Unicode scalar value               |
| Range      | U+0000 to U+10FFFF (excluding surrogates) |
| Size       | 1-4 bytes (encoding dependent)            |

**Array semantics:**

- `char` — single character
- `char[N]` — fixed-size string of exactly N characters
- `char[]` — semantically equivalent to `str`

**Encoding forms:**

`char` supports all encoding forms that `str` supports: `utf8` (default), `ascii`, `utf16`, `utf16le`, `utf16be`, `latin1`.

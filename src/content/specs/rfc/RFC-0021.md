# RFC-0021: Declaration Bundle Format

## Abstract

This RFC specifies the Declaration Bundle format, the JSON serialization of compiled Kintsu schemas for registry distribution and tooling integration. The format captures type definitions without source spans, suitable for consumption by code generators and other downstream tools.

## Motivation

Compiled schemas need a standardized interchange format for:

1. **Registry Storage** - Publish packages to schema registries
2. **Code Generation** - Feed type definitions to language-specific generators
3. **Tooling Integration** - IDE support, documentation generators, analyzers
4. **Cross-Platform Distribution** - Share compiled schemas without source

The declaration bundle is a "binary" output format (JSON) that strips source locations while preserving all type information needed for consumption.

## Specification

### Output Format

Declaration bundles are JSON files with the `.kintsu.json` extension:

```text title="Bundle filename"
my-package-1.0.0.kintsu.json
```

### Version Envelope

The bundle uses a versioned envelope with tagged content:

```json title="Declaration bundle envelope"
{
  "version": "v1",
  "declarations": {
    "root": { ... },
    "dependencies": { ... }
  }
}
```

The outer structure is `DeclarationVersion`, which wraps the inner `DeclarationBundle`.

### DeclarationBundle Structure

```json title="DeclarationBundle"
{
  "version": "v1",
  "declarations": {
    "root": {
      "package": "my-package",
      "namespaces": { ... },
      "external_refs": [ ... ]
    },
    "dependencies": {
      "dep_a": { ... },
      "dep_b": { ... }
    }
  }
}
```

| Field          | Type                                 | Description                                     |
| -------------- | ------------------------------------ | ----------------------------------------------- |
| `root`         | TypeRegistryDeclaration              | The compiled package                            |
| `dependencies` | Map<String, TypeRegistryDeclaration> | Compiled dependencies (keyed by namespace name) |

### TypeRegistryDeclaration

Each package (root or dependency) is represented as:

```json title="TypeRegistryDeclaration"
{
  "package": "my-package",
  "namespaces": {
    "types": { ... },
    "api": { ... }
  },
  "external_refs": [
    {
      "context": { "package": "dep_a", "namespace": ["types"] },
      "name": "User"
    }
  ]
}
```

| Field           | Type                   | Description                                             |
| --------------- | ---------------------- | ------------------------------------------------------- |
| `package`       | String                 | Package name (kebab-case)                               |
| `namespaces`    | Map<String, Namespace> | Namespace names (without package prefix) to definitions |
| `external_refs` | Array of TypeRef       | External type references used by this package           |

### Namespace Structure

Each namespace contains its name, type definitions, and optional default form metadata:

```json title="Namespace"
{
  "types": {
    "name": "types",
    "default_form": null,
    "types": [
      { "definition_type": "struct", ... },
      { "definition_type": "enum", ... },
      { "definition_type": "type_alias", ... }
    ]
  }
}
```

| Field          | Type                    | Description                                             |
| -------------- | ----------------------- | ------------------------------------------------------- |
| `name`         | String                  | Namespace name                                          |
| `default_form` | FormMetadata \| null    | Default form for fields in this namespace (from `#![]`) |
| `types`        | Array of TypeDefinition | Type definitions in this namespace                      |

When `default_form` is present, it captures the namespace-level `#![form(...)]` attribute. This enables tooling to display namespace-level formatting policies.

### Type Definitions

Type definitions use a `definition_type` field to indicate the kind:

#### Struct

```json title="Struct definition"
{
  "definition_type": "struct",
  "name": "User",
  "fields": [
    {
      "name": "id",
      "ty": { "type": "builtin", "ty": "u64" },
      "optional": false,
      "form": null
    },
    {
      "name": "email",
      "ty": { "type": "builtin", "ty": "str" },
      "optional": true,
      "form": null
    }
  ],
  "meta": { "version": 1 }
}
```

Field properties:

| Field      | Type                 | Description                                |
| ---------- | -------------------- | ------------------------------------------ |
| `name`     | String               | Field name                                 |
| `ty`       | TypeRef              | Field type reference                       |
| `optional` | Boolean              | Whether the field is optional              |
| `form`     | FormMetadata \| null | Form metadata for serialization transforms |

#### Enum (Value)

```json title="Enum definition"
{
  "definition_type": "enum",
  "name": "Status",
  "enum_def": {
    "enum_type": "int",
    "variants": [
      { "name": "Active", "value": 0 },
      { "name": "Inactive", "value": 1 },
      { "name": "Pending", "value": 2 }
    ]
  },
  "meta": { "version": 1 }
}
```

The `enum_type` can be `"int"` for integer values or `"str"` for string values.

#### Type Alias

```json title="Type alias definition"
{
  "definition_type": "type_alias",
  "name": "UserId",
  "target": { "type": "builtin", "ty": "u64" },
  "meta": { "version": 1 }
}
```

Aliases can target builtin types or named types:

```json title="Type alias with named reference"
{
  "definition_type": "type_alias",
  "name": "UserRef",
  "target": {
    "type": "named",
    "reference": {
      "context": { "package": "other_pkg", "namespace": ["types"] },
      "name": "User"
    }
  },
  "meta": { "version": 1 }
}
```

### Form Metadata

Form metadata captures serialization transform chains for fields. The `form` property is present on fields and as `default_form` on namespaces.

```json title="Structure"
{
  "chain": [{ "format": "base64" }, { "format": "gzip" }, { "format": "json" }],
  "precision": null
}
```

| Field       | Type                | Description                                              |
| ----------- | ------------------- | -------------------------------------------------------- |
| `chain`     | Array of FormatSpec | Transform chain in sequence order (encoded to canonical) |
| `precision` | String \| null      | Precision for complex/f8 types (e.g., "f64", "e4m3")     |

#### Format Specifications

Each element in the chain is a format specification object:

**Builtin formats** use the `format` key:

```json title="Builtin format"
{ "format": "json" }
{ "format": "gzip" }
{ "format": "base64" }
```

**Parameterized formats** include additional keys for options:

```json title="Parameterized format"
{ "format": "csv", "headers": false, "delimiter": "\t" }
{ "format": "json", "pretty": true, "indent": 4 }
{ "format": "xml", "namespace": "http://example.com/schema" }
```

**Custom formats** use `custom` and `algorithm` keys with optional `category`:

```json title="Custom format"
{ "custom": "compress", "algorithm": "lzo", "category": "binary" }
{ "custom": "encode", "algorithm": "base58", "category": "text" }
{ "custom": "mime", "algorithm": "application_vnd_api_json", "category": "text" }
```

The `category` field is optional and defaults based on the function kind (`compress` -> binary, `encode` -> text, `mime` -> inferred from pattern).

#### Chain Sequence Order

The chain is stored in **sequence order** from outermost (encoded) to innermost (canonical):

```kintsu
#[form(base64 = gzip = json)] cursor: Cursor
```

Serializes to:

```json
{
  "chain": [{ "format": "base64" }, { "format": "gzip" }, { "format": "json" }]
}
```

This ordering enables codegen to iterate forward for encoder pipelines or backward for decoder pipelines.

#### Complex Number Forms

Complex fields require form with precision:

```json title="Complex field with polar form"
{
  "name": "angle",
  "ty": { "type": "builtin", "ty": "complex" },
  "optional": false,
  "form": {
    "chain": [{ "format": "polar" }],
    "precision": "f64"
  }
}
```

#### f8 Minifloat Forms

f8 fields require form specifying the variant:

```json title="f8 field with E4M3 form"
{
  "name": "weight",
  "ty": { "type": "builtin", "ty": "f8" },
  "optional": false,
  "form": {
    "chain": [{ "format": "e4m3" }],
    "precision": null
  }
}
```

#### decimal Form (Required)

`decimal` fields require form specifying precision and scale per IEEE 754-2008:

```json title="decimal field with precision/scale form"
{
  "name": "price",
  "ty": { "type": "builtin", "ty": "decimal" },
  "optional": false,
  "form": {
    "precision": 10,
    "scale": 2
  }
}
```

The backing type is derived automatically from precision: decimal32 (P 1-7), decimal64 (P 8-16), decimal128 (P 17-34). Bundles without form metadata on `decimal` fields are invalid.

#### duration Form (Required)

`duration` fields require form specifying resolution or format:

```json title="duration field with milliseconds form"
{
  "name": "elapsed",
  "ty": { "type": "builtin", "ty": "duration" },
  "optional": false,
  "form": {
    "variant": "ms"
  }
}
```

```json title="duration field with ISO 8601 form"
{
  "name": "interval",
  "ty": { "type": "builtin", "ty": "duration" },
  "optional": false,
  "form": {
    "variant": "iso8601"
  }
}
```

Valid variants: `ms`, `us`, `ns` (numeric), `iso8601`, `iso8601ext` (string). Bundles without form metadata on `duration` fields are invalid.

#### char Encoding Forms

`char` fields may specify encoding forms for character encoding control:

```json title="char field with ASCII encoding"
{
  "name": "code",
  "ty": { "type": "builtin", "ty": "char" },
  "optional": false,
  "form": {
    "chain": [{ "format": "ascii" }]
  }
}
```

When no form is specified, `char` defaults to UTF-8 encoding. The form is optional for `char` (unlike `decimal` and `duration`).

#### Namespace Default Form

Namespaces with `#![form(...)]` store the default:

```json title="Namespace with default form"
{
  "name": "physics",
  "default_form": {
    "chain": [{ "format": "polar" }],
    "precision": "f64"
  },
  "types": [...]
}
```

Fields inherit this default unless they specify their own `form`. The bundle stores the **resolved** form on each field (explicit values, not inheritance markers), but `default_form` is preserved for tooling visibility.

#### Custom Formats with Explicit Categories

Custom formats may include explicit output categories for chain validation:

```json title="Custom format with explicit category"
{
  "name": "data",
  "ty": { "type": "builtin", "ty": "binary" },
  "optional": false,
  "form": {
    "chain": [
      { "custom": "compress", "value": "lzo", "category": "binary" },
      { "format": "json" }
    ],
    "precision": null
  }
}
```

The `category` field explicitly declares the output category:

- `"text"`: Transform outputs text representation
- `"binary"`: Transform outputs binary representation
- Omitted: Use implicit default based on custom format kind

This enables codegen plugins to validate custom format chains without hardcoded knowledge of every custom format's behavior.

### Type References

Types are referenced using structured objects:

#### Builtin Types

```json title="Builtin type references"
{ "type": "builtin", "ty": "u64" }
{ "type": "builtin", "ty": "str" }
{ "type": "builtin", "ty": "bool" }
{ "type": "builtin", "ty": "datetime" }
```

Extended integer types (128-bit and 256-bit):

```json title="Extended integer type references"
{ "type": "builtin", "ty": "i128" }
{ "type": "builtin", "ty": "u128" }
{ "type": "builtin", "ty": "i256" }
{ "type": "builtin", "ty": "u256" }
```

Extended float types (IEEE 754-2008):

```json title="Extended float type references"
{ "type": "builtin", "ty": "f128" }
{ "type": "builtin", "ty": "f256" }
```

Form-required builtin types (must have accompanying form metadata):

```json title="Form-required builtin type references"
{ "type": "builtin", "ty": "decimal" }
{ "type": "builtin", "ty": "duration" }
{ "type": "builtin", "ty": "char" }
```

#### Named Types (Same Package)

```json title="Named type reference (local)"
{
  "type": "named",
  "reference": {
    "context": { "package": "my_pkg", "namespace": ["types"] },
    "name": "User"
  }
}
```

#### Named Types (External Package)

```json title="Named type reference (external)"
{
  "type": "named",
  "reference": {
    "context": { "package": "other_pkg", "namespace": ["types"] },
    "name": "ExternalType"
  }
}
```

The `context` object contains:

- `package`: The package namespace name (snake_case)
- `namespace`: Array of namespace path segments

### Complete Example

```json title="my-package-1.0.0.kintsu.json" collapse={4-64, 66-92}
{
  "version": "v1",
  "declarations": {
    "root": {
      "package": "root-pkg",
      "namespaces": {
        "types": {
          "name": "types",
          "types": [
            {
              "definition_type": "struct",
              "name": "RootPkgData",
              "fields": [
                {

                },
                {
                  "name": "status",
                  "ty": {
                    "type": "named",
                    "reference": {
                      "context": {
                        "package": "root_pkg",

                      },
                      "name": "RootPkgStatus"
                    }
                  },
                  "optional": false
                }
              ],
              "meta": { "version": 1 }
            },
            {
              "definition_type": "enum",
              "name": "RootPkgStatus",
              "enum_def": {
                "enum_type": "int",
                "variants": [
                  { "name": "Active", "value": 0 },
                  { "name": "Inactive", "value": 1 },
                  { "name": "Pending", "value": 2 }
                ]
              },
              "meta": { "version": 1 }
            },
            {
              "definition_type": "type_alias",
              "name": "PkgRef",
              "target": {
                "type": "named",
                "reference": {
                  "context": { "package": "dep_pkg", "namespace": ["types"] },
                  "name": "DepData"
                }
              },
              "meta": { "version": 1 }
            }
          ]
        }
      },
      "external_refs": [
        {
          "context": { "package": "dep_pkg", "namespace": ["types"] },
          "name": "DepData"
        }

      "dep_pkg": {
        "package": "dep-pkg",
        "namespaces": {

```

### Checksum Computation

The declaration bundle checksum (used in lockfiles) is computed as:

1. Serialize the `DeclarationBundle` to canonical JSON (sorted keys, no extra whitespace)
2. Compute SHA-256 hash of the UTF-8 bytes
3. Encode as `sha256:{hex}`

## Rationale

### JSON Format

JSON was chosen for declaration bundles because:

- Universal parsing support across languages
- Human-readable for debugging
- Efficient tooling ecosystem
- Suitable for HTTP API responses (registries)

### Stripped Spans

Source spans are stripped because:

- Not needed for code generation
- Reduces file size significantly
- Avoids leaking internal source structure
- Checksums remain stable across reformats

### Inline Dependencies

Including compiled dependencies in the bundle:

- Enables offline code generation
- Single file contains everything needed
- Simplifies tooling integration
- Dependencies are immutable once locked

### TypeRegistryDeclaration Name

The "TypeRegistry" name reflects:

- Designed for registry storage/retrieval
- Contains only type information (no source)
- "Declaration" indicates these are declarations, not implementations

## Acceptance Criteria

- [ ] AC-1: Compiler outputs valid JSON matching this specification
- [ ] AC-2: All type definitions serialize correctly
- [ ] AC-3: External references are tracked in the `external` array
- [ ] AC-4: Checksum computation is deterministic
- [ ] AC-5: Bundle can be deserialized and used for code generation
- [ ] AC-6: Dependencies are included when specified
- [ ] AC-7: Form metadata is serialized on fields and namespace defaults
- [ ] AC-8: Form-required types (decimal, duration, f8, complex) include form metadata
- [ ] AC-9: Extended builtin types (i128, u128, i256, u256, f128, f256) serialize correctly

## Backwards Compatibility

This is the initial specification of the declaration bundle format. The version envelope ensures future versions can extend without breaking existing parsers.

Consumers encountering unknown versions SHOULD:

1. Check if `declarations` key exists (v1+ structure)
2. Attempt to parse as latest known version
3. Report clear errors for incompatible formats
